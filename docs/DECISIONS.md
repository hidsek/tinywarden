# tinywarden 検討記録

SPECに書いた決まりの理由、経緯、測った結果、調べた結果、まだ決まっていないことを残す。決まった内容そのものは [SPEC.md](SPEC.md) に書く。

## 動作確認の記録

- 2026-11-18〜19: 実機（ESP32-S3 SuperMini）で、拡張機能（Chrome）からの登録・ログイン・同期、パスワード付きJSONのインポートを確かめた
- 2026-11-19: 開発用ビルドで、偽の暗号文の約800件（ログイン750、カード40、メモ10、フォルダ3）のインポート、同期、1件の編集と削除、再起動後の読み込み、大掃除の繰り返しを確かめた

## ネットワーク

### ゲートウェイとDNSを渡さない（2026-11-18）

- 最初はESP-IDFのWi-Fiアクセスポイント用の既定の設定のまま、DHCPでゲートウェイとDNSに `192.168.237.1` を渡していた
- macOSでは、新しく出てきた「Espressif Device」がWi-Fiより上の順位に入り、全部の通信とDNSが機器に向いて、挿しているあいだインターネットが止まった（そのせいでClaude Codeも止まった）
- `esp_netif_dhcps_option` で `ROUTER_SOLICITATION_ADDRESS` と `DOMAIN_NAME_SERVER` を配らないようにした（`usb_net.c`）
- Mac側で、サービスの順位を下げるか、ゲートウェイなしの固定IPにしても防げる（予備の手）

### 80番が起動しなかった（2026-11-18）

- HTTPSのサーバー（`esp_https_server`）の内部の制御用ポートの既定値は32769。HTTPのサーバーにも32769を指定していたので、`bind` に失敗していた
- HTTPは既定の32768にした
- ついでに `LWIP_MAX_SOCKETS` を10→16、80番の同時接続を3にした（原因ではなかったが、HTTPSとHTTPが両方とも上限まで使うと10では足りないため残した）

### `192.168.237.x` を選んだ理由

家のLAN（`192.168.1.x`）とVPN（`10.x`）を避けるため。

## 登録とログイン

### 登録用のトークンが空になっていた（2026-11-18）

- 32バイトの乱数のbase64は44文字＋終端で45バイト要るのに、領域（`TOKEN_LEN`）が44バイトだった。mbedTLSが失敗して空の文字列を返し、拡張機能は「確認メールを送った」と受け取って先に進めなかった
- リフレッシュトークンも同じ領域の大きさを使っていた
- 48バイトにした

### ボタンを押す場面

- 「その場にいる人」の確認で、2要素認証の代わり。Macの中の悪い仕組みや、盗んだパスワードだけでは、ログインもアカウントの作成もできないようにするため
- ロック解除は拡張機能の中で済み、トークンの更新でもボタンは要らないので、押すのは新しい機器でのログインくらい。残す価値があると判断した
- 拡張機能は待っているあいだ何も表示しないので、LEDで知らせることにした

### サーバー側のPBKDF2を10,000回にした理由

- ログインのたびにESP32で計算するので、回数を増やすと待ち時間が延びる
- 総当たりの強さは、拡張機能側の鍵の導出（PBKDF2 60万回か、Argon2id）で決まる。サーバー側の回数はそこに足されるだけなので、減らしても弱くならない
- 構想メモ（vaultの `Inbox/tinywarden（ESP32のUSBパスワード保管庫・構想）.md`）には、Vaultwardenは10万回と書いてある。本家のBitwardenは確かめていない

### バックアップコードを作らない理由

- マスターパスワードは、どんな作りでも復旧できない（暗号化の鍵がマスターパスワードから作られ、サーバーはその鍵を持たない）。本家も同じ
- 本家の「リカバリーコード」は2段階ログインを外すためのもので、マスターパスワードの代わりではない。tinywardenの2段階目は物理的なボタンなので、外すものが無い
- 保管庫を開けるコードを作れば「2つ目のマスターパスワード」になり、盗まれるものが増えるだけ

## 保存の形

### 経緯

| 時期 | 作り | 結果 |
|---|---|---|
| v0.1 | FAT（4KB単位、wear leveling）、1件1ファイル、一時ファイルを書いてから名前を変える | 約800件（約1.1MBの送信データ）が入らなかった（必要約800ブロック、空き約700ブロック） |
| 2026-11-18 | プログラム用の区画を1.5MB→1MBにして、保管庫を2.5MB→2.9MBに広げた | 約700件分。まだ足りない |
| 2026-11-18 | FATを512バイト単位（電源断に強いSAFE方式）にした | 約1,270件入るが、1件約1秒。約800件で約13分の見込み。実際に約200件で手動でリセットした |
| 2026-11-19 | 16個のフォルダに分け、新しい項目は一時ファイルを使わずに書いた | 1件1.0〜1.1秒（古いやり方は1.2〜1.5秒で、件数とともに遅くなった） |
| 2026-11-19 | ログ方式（区画に追記、FATなし） | 約800件のインポートで15秒。1件30〜47ミリ秒。約1,310件入る |

- 「1件1ファイル」のままだと、速さと件数がトレードオフになる（4KB単位は速いが入らない、512バイト単位は入るが遅い）。ファイル単位の無駄をやめたので、両方が良くなった
- 512バイト単位が遅いのは、512バイト書くたびに4KBの消去と書き込みが起き、SAFE方式ではそれが2回ずつになるため
- 1KB単位は選べない（wear levelingの単位は512か4,096だけ）

### 検討して選ばなかった案

| 案 | 選ばなかった理由 |
|---|---|
| 512バイト＋速さ優先の方式（PERF） | 約2倍速いだけ。書き込み中に電源が切れると、同じ4KBにある他のデータや管理表まで壊れる |
| 4KB単位で、十数件を1ファイルにまとめる | 速くなるが、壊れたときに十数件を巻き込む。ログ方式のほうが速さも電源断への強さも上 |
| インポートをストリームで処理する | 全部入るかを先に判定できなくなる。Bitwardenはフォルダの割り当てを項目の後に送るので、書き込みが2倍になる。足りないのはメモリではなく保存領域だった |
| 大掃除を「エクスポートして入れ直す」でやる | 作業中に消える危険、項目のIDが全部変わる、履歴が消える、毎回人の操作が要る。大掃除は暗号文を移すだけなので、機器だけでできる |
| LittleFS | 小さいファイルでも1ブロック（4KB）を使うので、4KB単位のFATと同じ問題になる |

### 大掃除で、消したはずの項目が復活した（2026-11-19、ホストのテストで発見）

- 同じ区画に「古い保存の版」（前のほう）と「削除の印」（後ろのほう）があり、印を「もう要らない」と決めて写さずに消去を始め、後ろから消している途中で電源が切れると、前のほうの古い版だけが残る
- 直し方: 古い版の数え直しと、要らない削除の印を外すのは、消去が全部終わってからにした。あわせて、古い版の数は「保存」だけ数えることにした（最初の直し方では、外した後の削除の印を数え直して1つ多く引いてしまい、同じ症状が残った）
- 直した後、乱数を40通り変えて、合計600回以上の電源断でも、消えたり復活したりしなかった

### 実機での大掃除（2026-11-19）

- 本物の項目764件を入れたまま、偽の900件を書いて消すのを3回繰り返した。容量いっぱい近くで大掃除が48回起きた
- 書き込みは1件30〜47ミリ秒。同期し直した764件は、1件も消えたり変わったりしていなかった

### 寿命の見積もり

- 前提: 1区画（4KB）あたり10万回の書き換え（データシートでよくある値。このチップでは確かめていない）。保存領域は752区画なので、全体で約7,500万回
- 読むだけ（同期、表示、ロック解除）では保存領域に書かない
- FATの頃の見積もり（1件の作成で約16回、編集で約24回の消去）でも、月10件の編集で約2万5,000年、年1回のインポートで約5,800年。ログ方式はもっと少ない
- 実際の寿命は、データの保持期間（多くのデータシートで約20年）、USB端子のすり減り、部品の劣化で決まる

## 電源断への対策と結果

### どう守っているか

| 書いている最中のもの | 対策 | 切れたあと |
|---|---|---|
| 項目・フォルダ・ユーザーの記録 | 1回で書き、CRCを付ける。上書きしない | 書きかけの1件だけが捨てられ、前の版が残る。その操作は拡張機能に成功と返していない |
| 大掃除の写し | 写し終わるまで元を消さない | 同じ版が2つあるだけ。通し番号の大きいほうを使う |
| 大掃除の消去 | 後ろのセクターから消す。古い版の数え直しと、要らない削除の印を外すのは、消去が全部終わってから | 中途半端な区画は起動時に消し直す。消した項目は復活しない |
| 新しい区画の見出し | CRCを付ける | 正しくない見出しの区画は、起動時に消し直す |
| インポート | 1件ずつ記録として書く | そこまでの件数が入った状態になる（全部か無しかではない。今後の課題） |
| NVS（失敗の回数、時計、証明書） | ESP-IDFのNVSの仕組みに任せる | 失敗の回数は照合の前に増やして保存するので、照合の途中で抜いても回数は戻らない |

### 確かめた結果

| 確かめ方 | 結果 |
|---|---|
| ホストのテスト: 書き込み・写し・消去の途中の、好きなバイトで電源を切る（NORフラッシュのまね。書きかけのバイトは一部のビットだけ0、消しかけのセクターは途中から先がでたらめ） | 2026-11-19、乱数40通り・12万回の操作の中で571回電源を切り、書きかけの記録を1,743件見つけて捨てた。成功と返した操作が消えたことも、消した項目が復活したことも0回 |
| ホストのテストで見つかった不具合 | 大掃除の消去の途中で切れると、消した項目が復活した（上の「保存の形」）。直してから上の結果 |
| 実機: 再起動（ソフトウェアの再起動）のあと読み直す | 764件が1件も変わらずに残った |
| 実機: 大掃除を48回起こしたあと読み直す | 764件が1件も変わらなかった |

### 確かめていないこと

- **実機で、書き込みの最中に本当に電源を抜くテストはしていない。** 上の結果は、ホストでのまねと、実機での「書き終わってからの再起動」だけ
- 本物のフラッシュは、書き込みや消去の途中で切れたときに、まねとは違う壊れ方をするかもしれない（たとえば、消しかけのセクターが、読むたびに違う値を返す）
- ESP-IDFの `esp_partition_write` が、途中で切れたときにどこまで書いているか（ページ単位か）は確かめていない
- 実機で確かめるなら: 大掃除が起きる量を書き続けながら、USBを抜き挿しする（リレーで電源を切る道具があると、何百回もできる）

## インポート

### 1MBの上限を外した（2026-11-18）

- 最初は1回1MBに決めていた（余裕を見ただけの値）。実際の送信データが1,143KBで断られた
- PSRAMで今取れる一番大きい塊から256KBを引いた値にした。ログ方式の本番の版で約1,696KB

### エラー表示で拡張機能が落ちた（2026-11-18）

- 拡張機能のインポート画面は、`validationErrors` のキーから「何件目か」の番号を読もうとする。キーが `""` だと `null[0]` になり、`Cannot read properties of null (reading '0')` と出た
- インポートのエラーだけ `validationErrors: null` にした

### 形式ごとの違い（調べた結果）

| 形式 | 入るもの |
|---|---|
| パスワード付きJSON（「ファイルのパスワード」の種類） | 全部。「アカウント制限」の種類は、エクスポートしたアカウントにしか入らない |
| JSON | 全部。ファイルは暗号化されていない |
| CSV | ログインとセキュアメモだけ |

どれも添付ファイルは入らない。拡張機能がMac上で暗号化してから送るので、機器が受け取る形は同じ。

## 同期

- 最初は1件ずつ送っていて、約800件で約12秒かかった
- 8KBずつまとめて送るようにした。本番の版で、空の保管庫の同期が通ることは確かめた。速さはまだ測っていない

## LED

- 起動直後に赤く光っていたのは、色つきLED（WS2812、GPIO48）が勝手な色で点いていたもの。起動時に消すようにした
- 青く点滅し続ける「BAT」のLEDは、充電回路が電池を探しているもの。ファームウェアからは消せない。テープで覆う、ケースに入れる、部品を外す、が対処

## 開発の道具

### 書き込みモードへの再起動が動かない（未解決）

- やりたいこと: ネット越しに書き込みモードにして、BOOTとRSTを押さずに書き込む
- 1回目: `RTC_CNTL_FORCE_DOWNLOAD_BOOT` を立てて `esp_restart()` → ふつうに起動し直した
- 2回目: USBの回路をUSB-Serial-JTAGに戻してから（`RTC_CNTL_SW_HW_USB_PHY_SEL` を落とす）同じことをした → ふつうに起動し直した
- 3回目: `esp_restart()` がRTCの見張りタイマーを1秒で仕掛けることをESP-IDFのソースで確かめ（`system_internal.c`）、それを止めてから `esp_rom_software_reset_system()` でリセットした → 基板が応答しなくなり、RSTを押すまで戻らなかった
- 推測: ROMの書き込みモードが、TinyUSBが使っていたUSB-OTGの状態のままになっている。ESP-IDFの `usb_console.c` のように、USB-OTGの状態を残す仕組み（`usb_dc_prepare_persist` と `chip_usb_set_persist_flags`）が要るのかもしれない

### ボタンを省くビルドを作った理由

夜のあいだに、無人で登録・ログイン・インポート・大掃除を実機で試すため。本番の版では無効にした。

## 本家のBitwarden・Vaultwardenとの比較

狙い（2026-11-16の構想）: Bitwardenと同じ使い心地のまま、保管庫をクラウドにもサーバーにも置かず、USBで挿した基板の中だけに置く。対象は「暗号化されていても、パスワードの保管庫がクラウドにあるのが嫌な人」。

### 同じところ

- 使うのは公式の拡張機能そのもの（改造なし）。自動入力、パスワード生成、パスキーも同じ
- 保管庫の中身の暗号化は拡張機能がやるので、暗号のやり方は本家と同じ。サーバー（基板）は暗号文しか持たない
- エクスポートとインポートの形式も同じ。いつでも本家やVaultwardenに戻れる

### 比べた表

| 観点 | Bitwarden（クラウド） | Vaultwarden（自宅サーバー） | tinywarden |
|---|---|---|---|
| 保管庫の置き場所 | Bitwardenのクラウド | 自分のサーバー | USBの基板の中だけ |
| サーバーの運用 | 不要 | 要る（更新、バックアップ、公開の設定） | 不要 |
| 使うのに要るネットワーク | インターネット | 自宅のネットかVPN | 要らない（USBだけ） |
| 別のパソコンに移るとき | どこでもログインできる | ネットが届けばできる | 基板を挿し替える。ネットは要らない。そのパソコンで証明書を信頼させ、ログイン（ボタン）が要る |
| 複数の機器での同時の同期 | できる | できる | できない（基板は1つで、挿したパソコンだけ） |
| スマホ | 使える | 使える | まだ使えない（DECISIONSの「スマホ」） |
| 2段階認証 | アプリのコード、鍵など | 同じ | 基板のボタン（その場にいないと押せない） |
| 総当たり（オンライン） | 回数制限 | 回数制限（設定しだい） | ボタン必須、10回で全消去 |
| サーバーが破られたとき | 全利用者の暗号文が持ち出されうる（2022年のLastPassのような事件の型） | 自分の暗号文が持ち出されうる | 遠くからは破れない。基板を物理的に取る必要がある |
| 基板や機器を盗まれたとき | 関係なし | サーバーの機器による | 今は暗号文を読み出され、手元で総当たりされうる（中身を閉じるまで） |
| 抜いたら | 関係なし | 関係なし | 全員ログアウト（緊急時の止め方になる） |
| 壊れた・なくしたとき | クラウドに残る | 自分のバックアップしだい | 自分のバックアップしだい（無ければ全部失う） |
| 添付・Send・組織・緊急アクセス | ある（一部は有料） | ある | 無い |
| 拡張機能の更新への追従 | 本家がやる | Vaultwardenの開発者がやる | 自分でやる（拡張機能が変わると、ファームウェアを直す必要がある） |
| 第三者の監査 | ある | 無い（オープンソース） | 無い |
| お金 | 無料〜有料 | サーバー代 | 基板代（数百円〜千円台） |

### 有意な点（tinywardenを選ぶ理由になるもの）

1. **クラウドにもサーバーにも保管庫が無い。** サーバーへの攻撃でまとめて持ち出される、という型の事件が起きようがない
2. **ネットワークが要らない。** 別のパソコンへ移るのも、基板を挿し替えるだけ。インターネットにつながらない場所でも使える
3. **物理的なボタンが2段階認証になる。** 遠くにいる攻撃者は、パスワードを盗んでもログインできない
4. **サーバーの運用が無い。** 更新やバックアップのためにサーバーを動かし続ける必要が無い（バックアップのファイルは自分で取る）
5. **抜けば全員ログアウト。** なくした・盗られたと思ったら、抜くだけで止められる（挿していた側のトークンは全部使えなくなる）

### 弱い点（選ばない理由になるもの）

1. **基板を盗まれると、今は暗号文を読み出せる。** マスターパスワードが長くないと、手元で総当たりされる。中身を閉じれば消せる弱点（DECISIONSの「中身を閉じる機能」）
2. **基板が1つ。** 複数の機器で同時に使えない。スマホでもまだ使えない
3. **バックアップは自分の責任。** 取っていなければ、壊れたら全部失う
4. **拡張機能の変化に自分で追いつく必要がある。** Bitwardenの仕様が変わると、ある日ログインできなくなるかもしれない
5. **監査を受けていない。** 暗号そのものは拡張機能がやるので影響は小さいが、ログインの確認やトークンの作りは自作

### 向いている使い方（今のところの結論）

- ふだんの全部のパスワードを任せるより、**「クラウドに置きたくない一部の秘密」用の2つ目の保管庫**に向いている
- スマホを含めて全部の機器で使いたいなら、本家かVaultwardenのほうがよい。tinywardenでやるなら、家庭内LAN版と自分用の認証局が要る

## 暗号化について（調べた結果）

- 保管庫の中身の暗号化（AES-256とHMAC、マスターパスワードからの鍵の導出）は、拡張機能がやるので、本家のBitwardenと同じ
- 違うのは、保存の形と、サーバー側の守り方（証明書が自分で作ったもの、保存場所での追加の暗号化が無い、2段階目がボタン、10回で全消去）
- いちばんの違いは、基板を持っていかれると暗号文をまるごと読み出されること

## 中身を閉じる機能（未実施）

| 機能 | 防ぐもの |
|---|---|
| フラッシュの暗号化 | esptoolで読み出されても中身が読めない |
| NVSの暗号化 | 証明書の秘密鍵と失敗回数を守る（フラッシュの暗号化が前提。区画 `nvs_keys` が要る） |
| セキュアブート（v2） | 署名していないファームウェアは起動しない |
| 書き込みモードの無効化（か、安全な書き込みモード） | 書き込みモードから読む道を閉じる |
| JTAGの無効化 | デバッガーから読む道を閉じる |

- どれもeFuseを焼くので戻せない。開発用の基板は閉じない
- 進め方の案: 機能が固まったら新しい基板を用意し（BAT表示の無いもの、技適のあるものも検討）、開発モードのフラッシュ暗号化で流れを試してから、リリースモードとセキュアブートにする。eFuseを焼くコマンドは人が打つ

- 月1回のパスワード付きJSONの保存、予備の機器、クラウドに暗号化した控えを置く、などの例は MANUAL に書いた

## 控えの保存にマスターパスワードを求める

管理ページの「控えを保存」は、最初はBOOTだけで出していた。中身を閉じていない今は、基板を持つ人はフラッシュを直接読めるので、守りは変わらない。ただ、中身を閉じたあとは、ここが暗号文を外に出す唯一の道になる。そこで、ログインと同じ確かめ方（メールとマスターパスワードのハッシュ、ボタン、失敗の回数）にした。

- マスターパスワードは管理ページの中で、拡張機能と同じ計算（PBKDF2）でハッシュにしてから送る。ブラウザの計算と `tw_backup.py` の計算が同じ値になることを、Macのnodeで確かめた
- 総当たりの材料という点では、同じ暗号文がログインした端末の中にもある。守りの中心は、やはりマスターパスワードの長さ

## 控えから戻す方法

戻すときは、移る先（新しいtinywarden、Bitwardenのクラウド、Vaultwarden）で新しくアカウントを作り、`tw_backup.py decrypt` で戻したJSONをインポートする。暗号文をそのまま機器に書き戻す機能は作らない（2026-11-19に決めた）。

- 新しいアカウントに入れ直すほうが、移る先を選ばない。tinywardenに不具合があっても、本家やVaultwardenに逃がせる
- 書き戻しは、同じアカウントの鍵のままでしか使えず、tinywarden同士でしか役に立たない
- `decrypt` は、Bitwardenの「パスワード付きのエクスポート」の形で書く（2026-11-19）。鍵は公式ソース（`BaseVaultExportService.buildPasswordExport`、`deriveVaultExportKey`）のとおり、ファイルのパスワードを、16バイトの乱数をBase64にした文字列を塩にしてPBKDF2-SHA256（60万回）にかけ、HKDFで伸ばす。暗号化されていないJSONは `--plain` のときだけ

## アプリの更新でログインできなくなったとき

tinywardenは公式のアプリを相手にする「非公式のサーバー」なので、アプリの更新で送り方や求める項目が変わると、ある日つながらなくなりうる。2026-11-19のiPhoneの「Unsupported grant type」（項目名の `_` まで `%5F` に置き換えて送ってくる）が、その例。

**備え**
- データは標準の形の暗号文なので、壊れも消えもしない。困るのは、暗号を解けるのが公式のアプリだけという点
- そこで、アプリに頼らない道を2つ用意した: 管理ページの「控えを保存」（BOOTで許可）と `tools/tw_backup.py`（`fetch` で取得、`decrypt` で機器なしにBitwardenの形のJSONへ）。月に1回の控えをMANUALで勧めている
- 管理ページの「つないできたアプリ（起動後）」に、アプリの名前・版・`Device-Type` と、最後のログイン失敗を出す。どの版から壊れたかがすぐわかる

**壊れたときの直し方**
1. 管理ページで、失敗した要求（パスとエラーの文章）と、アプリの版を見る
2. その版で何が変わったかを調べる。手本は Vaultwarden（同じ公式のアプリを相手にしていて、追いつくのが速い）
   - Vaultwardenの変更履歴とissueを、アプリの版やエラーの文章で探す（GitHub `dani-garcia/vaultwarden`）
   - 公式のアプリのソース（`bitwarden/clients`、`bitwarden/ios`、`bitwarden/android`）で、その版の変更を見る。iPhoneの件は `bitwarden/ios` の `RequestBody.swift` で原因がわかった
3. 直すまでのあいだ使うなら、古い版のアプリに戻す
   - ブラウザの拡張機能: `bitwarden/clients` のGitHubのリリースから古い版の拡張機能を落とし、ブラウザの開発者モードで手で入れる（自動更新は止まる。直ったら公式の版に戻す）
   - iPhone・Android: 古い版に戻すのは難しい。管理ページの控えと `tw_backup.py` で中身を取り出す
4. 最後の手段: 控えを `tw_backup.py decrypt` で戻し、本家のBitwardenかVaultwardenにインポートして、そちらで使う

## 同期の食い違い

USBなので、同時に基板とつながるのは1台だけ。挿し替えると次の同期でログアウトされ、ログインし直すときに全部を同期する。公式のアプリは、サーバーにつながらないと編集を保存できない。だから、ふだんは食い違いは起きない。

起きうるのは、同じパソコンで複数のアプリ（ChromeとEdgeの拡張機能など）が同時にログインしていて、片方が古い中身のまま同じ項目を保存したとき。最初は `lastKnownRevisionDate` を確かめずに捨てていたので、後から保存したほうが黙って勝っていた。2026-11-19に、本家とVaultwardenと同じく、保存されている更新時刻より古い中身からの保存を断るようにした（1秒の余裕つき）。アプリは「同期してから直して」と出す。基板の時計は起動をまたいでも戻らない（`clock.c`）ので、比べるのは基板の時計どうし。

## パスキー

Bitwardenは、パスキーそのものを保管庫の項目（`login.fido2Credentials`）に入れて使える。tinywardenは項目の中身をそのまま保存するので、特別な対応はしていない。

- 2026-11-19: インポートした保管庫に入っていたパスキーで、サイトにログインできた
- 2026-11-19: 新しいパスキーの登録（サイトでパスキーを作り、Bitwardenに保存する）もできた。項目の作成・更新と同じ道を通るので、特別な対応は要らなかった
- 新しく登録したパスキーを、別の機器で同期して使うのは、まだ確かめていない
- 入力の手間を減らすために、PicoKeys（pico-fido）を同じ基板に入れる案は採らない。ファームウェアが1MBの置き場所を超えそう、pico-fidoはAGPL-3.0で全体のライセンスが変わる、eFuseの鍵の置き場を取り合う、USBの作りが複雑になるため。手間はBitwardenのPINや生体認証での解除と、保管庫のパスキーで減らせる。専用のキーが欲しければ、別の基板に入れる

## Argon2idに変えられるようにした（2026-11-20）

- **理由:** 暗号文が盗まれたときの守りは、マスターパスワードの強さと、1回試すのにかかる手間（KDF）の掛け算。PBKDF2はGPUを並べるほど速くなる。Argon2idは1回ごとにメモリ（32MB）を使うので並べにくい。GPU 1台で1秒に試せる回数は、PBKDF2（60万回）で約1万回、Argon2id（32MB・6回・並列4）で数百回、という見積もり（メモリの転送速度からの概算で、測っていない）。差が出るのは中くらいの強さのパスワードで、でたらめな単語を1個足すほうが効く（約7776倍）。なのでマスターパスワードを長くするのが先で、Argon2idは保険
- **なぜ管理ページで変えるのか:** 公式のアプリは、アカウントを作るとき必ずPBKDF2にする（`DEFAULT_KDF_CONFIG`）。KDFを変える画面はWeb保管庫（`apps/web` の change-kdf）にしかなく、Web保管庫は基板に入らない。基板はマスターパスワードを知らないので、自分では変えられない。そこで、管理ページのブラウザの中で計算して、包み直した鍵だけを基板に送る
- **流れ:** BOOTは1回。`/tw/kdf/key` でパスワードを確かめ（ログインと同じボタンと失敗の回数）、今の包みと、2分で切れる1回きりのトークンを返す。ページが今のマスターキーでユーザーキーを開け、新しいマスターキーで包み直し、開け直して確かめてから `/tw/kdf` に送る。基板はユーザーの記録を1回の書き込みで置き換え、署名の鍵を作り直して全員をログアウトさせる（再起動は要らない）。保管庫の項目には触らない
- **Argon2idの計算:** ブラウザに無いので、`@noble/hashes` 2.0.1（MIT、純粋なJavaScript）を `firmware/web/vendor/` に置いた。自分で書くより、広く使われていて読みやすい実装を選んだ。WebAssemblyにしなかったのは、CSPで `wasm-unsafe-eval` を許したくないのと、Macで約1.4秒と十分速かったため。RFC 9106の試験値と、OpenSSL 3.6の `openssl kdf ARGON2ID` の結果で確かめた（`test/web/test_twcrypto.mjs`）
- **Bitwardenの決まり（ソースで確かめた）:** マスターキーは Argon2id v0x13（パスワード、SHA-256(メールを小文字にして前後の空白を除いたもの)、回数、メモリ MiB×1024 KiB、並列）、32バイト（`bitwarden-crypto` の `kdf.rs`）。パスワード付きのエクスポートも、アカウントと同じKDFの設定で、ソルトの文字列をSHA-256にかけて使う（`deriveVaultExportKey` = stretch(KDF)）
- **初期値:** 今のアプリがArgon2idを選んだときに入れる値（32MB・6回・並列4。以前の初期値の64MB・3回と重さはほぼ同じ）。iPhoneの自動入力の画面は使えるメモリが小さいので、メモリは増やさない
- **ページの作り:** 管理ページのスクリプトを `firmware/web/` の別のファイルにして、`/web/` から配る（`EMBED_FILES`）。ページにはCSPを付け、基板のスクリプトしか動かないようにした
- **確かめたこと（2026-11-20）:** 115件の保管庫で、PBKDF2からArgon2idに変え、拡張機能でログインし直し、ロックしてマスターパスワードで解除できた。別のサーバーで同じ設定にしたアカウントでは、iPhoneの自動入力も動いた
