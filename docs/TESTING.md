# tinywarden テスト

テストは3段ある。速いものから順に回す。

| 段 | 何を試すか | どこで | 道具 | かかる時間 |
|---|---|---|---|---|
| 1. ホスト | 保存の仕組み（`logstore.c`）だけ。電源断を含む | Mac | `test/host/test_logstore.c` | 1分ほど |
| 2. 実機API | ファームウェア全体を、APIから | 基板（開発用ビルド） | `test/device/device_test.py` | 10分ほど |
| 3. 受け入れ | 本物の拡張機能から、人が操作する | 基板（本番の版） | 下の確認表 | 15分ほど |

保存の形（`logstore.c`、`store.c`、区画）を変えたら1〜3を全部、APIだけ変えたら2〜3を回す。

## 1. ホストのテスト（`test/host/test_logstore.c`）

`logstore.c` をそのままMacでコンパイルし、NORフラッシュをまねた入れ物の上で動かす。

### まねているフラッシュの性質

- 書き込みは、ビットを1から0にしかできない（`mem &= data`）
- 消去は4KB単位で、全部を0xFFに戻す
- 電源断: 書き込みや消去に「あと何バイトで止まるか」を与えておき、そこで処理を打ち切る。書きかけのバイトは一部のビットだけが0になり、消しかけのセクターは途中から先がでたらめになる
- 打ち切ったあとは、メモリ上の状態を全部捨てて（電源が切れたのと同じ）、フラッシュの中身だけから起動し直す

### テストの中身

| テスト | 内容 | 合格の条件 |
|---|---|---|
| `test_basic` | 1件の保存・上書き・読み出し、ユーザーの保存、削除、2回目の削除、起動し直し、最近の変更 | 削除した項目が起動し直しても消えたまま。2回目の削除は「見つからない」。最近の変更が4件で、最新が削除 |
| `test_random`（8区画、200キー、2万回） | 保存・更新・削除をランダムに行い、正解の表（モデル）と比べる。997回ごとに起動し直す。たまに20KBの大きな記録を混ぜる | 起動し直すたびに、全部のキーの中身と件数がモデルと一致する |
| `test_random`（6区画、300キー、3万回） | 同じことを、容量の上限ぎりぎりで行う。大掃除がずっと起き、「空きが足りない」も起きる | 一致すること。「空きが足りない」以外のエラーが出ないこと |
| `test_random`（47区画、400キー、2万回） | 本物の区画の大きさで行う | 一致すること |
| `test_power_cuts`（6区画、60キー、3,000回×乱数2通り） | 3回に1回、操作の途中で電源を切る。半分は記録を書いている最中、半分はそのあとの大掃除の写しや消去の最中 | 電源断のあと、成功と返した操作は全部残っている。途中だった1件は、前の状態か新しい状態のどちらか。消した項目が復活しない |
| `test_vault`（47区画） | 1.5〜2.7KBの項目400件を入れ、10年分（1,200回）の編集をする | 起動し直して全部一致。消去の回数を表示する |
| `./t 40` | `test_power_cuts` だけを、乱数を40通り変えて回す（電源断の長時間テスト） | 全部合格 |

### 回し方

```sh
cd test/host
cc -std=c11 -O2 -g -Wall -Wextra -fsanitize=address,undefined -I../../firmware/main ../../firmware/main/logstore.c test_logstore.c -o t
ASAN_OPTIONS=detect_leaks=0 ./t       # 全部
ASAN_OPTIONS=detect_leaks=0 ./t 40    # 電源断だけを40通り
```

`-fsanitize` で、範囲外の読み書きや未定義の動作も見つける。電源断のテストは、わざとメモリを解放しないまま起動し直す（本物の電源断と同じ）ので、リークの検出は切っている。

## 2. 実機APIのテスト（`test/device/device_test.py`）

基板に、本物の拡張機能と同じ形の要求を送る。中身は暗号文の形をした乱数で、基板は暗号文を解釈しないので、同じ大きさの本物の保管庫と同じ道を通る。

### 準備

1. `firmware/sdkconfig` で `CONFIG_TW_DEV_DOWNLOAD_ENDPOINT=y` と `CONFIG_TW_DEV_SKIP_BUTTON=y` にする
2. 書き込みモードにして `./flash.sh --wipe`
3. 本物の保管庫が入っていないことを確かめる（テストは使い捨てのアカウントを作り、最後に全消去する）

### 回し方

```sh
python3 -I test/device/device_test.py               # 全部（10分ほど）
python3 -I test/device/device_test.py --quick       # 大掃除の繰り返しを省く
python3 -I test/device/device_test.py --wipe-first  # 最初に全消去してから
```

終わったら、本番の設定（2つとも無効）に戻して `./flash.sh --wipe` する。

### テストの中身

| 順 | 内容 | 合格の条件 |
|---|---|---|
| 0 | 管理ページが開ける、開発用ビルドである、ユーザーがいない | 3つとも満たす（満たさなければそこで止める） |
| 1 | 登録用のトークン、登録、ログイン、間違ったパスワード、空の同期 | トークンが43文字、登録とログインが200、間違いは400、同期は0件 |
| 2 | 壊れたインポート、800件のインポート（ログイン750、カード40、メモ10、フォルダ3）、同期 | 壊れたものは400で `validationErrors` が無い。インポートが200。件数・フォルダの割り当て・種類が送ったとおり |
| 3 | 1件の編集、1件の削除、同期 | 編集が反映され、削除した1件だけが無く、ほかは1件も変わらない |
| 4 | 再起動、古いトークン、ログインし直して同期 | 古いトークンは401（起動ごとに署名の鍵が変わる）。中身は3と同じ |
| 5 | 偽の900件を書いて消す、を3回（容量いっぱい近くで大掃除が起きる）、同期 | 900件とも書けて消せる。中身は3と同じ |
| 6 | 全消去 | 200 |

かかった時間（インポート、同期）と、大掃除のときの1件あたりの時間も表示する。

## 3. 受け入れの確認（本物の拡張機能、本番の版）

本番の版（開発用の設定を両方とも無効）を `./flash.sh --wipe` で書いてから、人が行う。

| 順 | 操作 | 確かめること |
|---|---|---|
| 1 | 挿す | Macのインターネットが止まらない（`netstat -rn -f inet \| grep default` が `en0` のまま） |
| 2 | 管理ページを開く | 赤字の「開発用ビルド」が出ていない。証明書のSHA-256がMacに登録したものと同じ |
| 3 | 拡張機能でアカウントを作る | 基板のLEDが光り、BOOTを押すと作れる。押さないと30秒で断られる |
| 4 | ログインする | 基板のLEDが光り、BOOTを押すとログインできる。管理ページの「直近の通信」に `GET /api/sync → 200` |
| 5 | パスワード付きJSONをインポートする | 成功。管理ページの件数がエクスポート元と同じ |
| 6 | 項目を1件作る、直す、消す | 拡張機能と管理ページの「最近の変更」の両方に出る |
| 7 | 抜いて挿し直す | ログアウトされる。ログインし直すと中身が同じ |
| 8 | 管理ページで「全部消す」 | BOOTを押すと消える。ユーザーが未登録になる |

## 4. 控えの道具のテスト（`test/host/test_tw_backup.py`）

`tools/tw_backup.py` の暗号の部分をMacで確かめる。`python3 -I test/host/test_tw_backup.py`

| 内容 | 合格の条件 |
|---|---|
| AES-256-CBCの復号（0〜70バイトと、1000・4096バイト） | opensslで暗号化したものが元に戻る |
| AES-256の公式の試験値（FIPS-197 付録C.3） | 一致 |
| 合成の保管庫（Bitwardenと同じ作り方で、opensslで暗号化） | フォルダ名、項目ごとの鍵を持つ項目、ユーザーの鍵だけの項目が戻る。サーバー用の欄が消える。ゴミ箱は除く。出力のファイルが自分だけ読める（0600） |
| 間違ったマスターパスワード | 「wrong master password」で止まる |

マスターキーの作り方（PBKDF2、HKDFでの伸ばし方）が本物と同じかは、このテストでは確かめられない（自分で作って自分で解くため）。本物の保管庫で `fetch` すると、ログインが通ることと、ユーザーの鍵が解けることで確かめられる。
